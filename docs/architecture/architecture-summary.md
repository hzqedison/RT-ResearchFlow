# RT-ResearchFlow 架构重梳理摘要

日期：2026-10-08。

目标是让产品更容易稳定迭代：测试者可以直接反馈问题，研发能够自行定位、复现、修复和验证；用户不再承担技术解释与反复协调的工作。

## 已经确定的分工

| 工作 | 负责人 | 处理范围 |
| --- | --- | --- |
| 架构与最终审查 | 当前顶级模型 | 模块边界、重要业务语义、数据恢复、交易状态、跨模块取舍 |
| 工程执行 | Sol | 具体实现、修复、集成、测试、打包发布 |
| 基础执行 | Luna | 文案、反馈模板、验收清单、低风险资料整理 |

分工已经用于本轮工作。复杂任务有明确写范围和验收条件，执行者遇到难点向主代理升级，普通技术问题由团队内部处理。完整规则已写入项目 AGENTS.md，后续沿用。

## 产品框架

仍然是一个 Windows / Mac 桌面产品。界面、业务用例、业务规则、数据和系统适配器分别负责自己的工作，现有功能按完整操作流程逐步迁移。

| 模块 | 用户得到的能力 | 架构要求 |
| --- | --- | --- |
| 配置与凭证 | 配置模型和数据源，保存后可继续使用 | 局部保存、明确错误、保留未修改配置 |
| 数据与日历 | 知道哪些数据可用、缺什么、如何补齐 | 来源与时间清楚，能力与当前可用状态分开 |
| 研究与 AI | 查资料、分析、查看依据 | 引用可追溯，任务失败可定位 |
| 策略与回测 | 验证规则和比较结果 | 保留版本与假设，不混淆信号收益和账户收益 |
| 交易与风险 | 本人确认后执行，并核对结果 | 明确状态、避免重复提交、未知结果先核实 |
| 账户与复盘 | 查看数量、成交、费用与策略结果 | 区分研究投组和真实账户事实 |
| 诊断与交付 | 报错可反馈，升级可恢复 | 统一错误编号、白名单反馈、测试与下载包一致 |

## 1.1 的优先顺序

1. 修复停止后旧调度任务可能重新登记的问题，统一退出和重启的清理顺序。
2. 统一升级前的一致性数据库快照，保留已有手动备份和数据目录保护。
3. 统一敏感接口的调用检查，并把普通错误转成可理解、可定位的结果。
4. 在现有诊断页接入标准脱敏反馈，测试者填写目标、结果和时间即可交给研发。
5. 完成配置、数据源、日历与下载中断的逐项回归，再扩展账户、交易与回测能力。

前三项来自源码盘点，已确定条件和验证办法；运行影响仍由隔离测试补证。完整迁移尚未完成，不能将设计目标当作当前安装包已有功能。

## 反馈如何减少中间转述

目标操作是：测试者打开诊断入口，预览并保存反馈文件，直接把文件与简短描述交给研发。标准文件包含版本、系统架构、错误编号和必要状态；业务数据备份仍单独保留，不自动作为反馈附件。

现有诊断页面和健康检查可以复用。新的纯逻辑错误与反馈模块先完成独立验证，再接入页面与运行流程。现阶段可先使用 [测试反馈模板](../quality/tester-feedback-template.md)。

本轮已实现 `electron/shared/supportDiagnostics.ts`，提供中文公开错误、关联编号校验和白名单反馈数据结构。42 项隔离测试及严格类型检查已通过，主代理已审查并修正能力状态契约；目前尚未接入界面或已有运行流程，因此不能称为已经上线的反馈功能。
