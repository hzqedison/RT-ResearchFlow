## 待修复发现

### R3 [P1] Windows 隔离 Python 的实际标准流编码尚未得到保证

最新状态：父任务已报告 `runPython` 在 spawn 参数最前显式加入 `['-X', 'utf8', ...args]`；新增 4 项编码测试由本审查独立执行通过。此项不再作为已知未修复的编码阻断项。真实链路由父任务报告成功，原始现场日志仍需归档；下文保留最初发现过程。

定位于本轮已读取、尚未包含父任务后续修复的 `electron/main/services/pythonDataSourceBridge.ts`：`:107` 仅设置环境变量 `PYTHONUTF8=1`，`:154` 使用 `-I` 启动隔离解释器，`:65` 通过 `ensure_ascii=False` 输出中文 JSON，`:142` 固定按 UTF-8 解码 stdout。

父任务真实探测报告：Python 3.13.13 / AKShare 1.19.1 的 `stock_zt_pool_em(date='20261008')` 返回 43 行，但 Windows 直接探测的中文列出现乱码；父任务指出 `-I` 忽略 `PYTHONUTF8`，正在检查实际 `stdout.encoding` 并增加显式 `-X utf8`。这是已报告的直接探测现象及待闭环的应用风险，不宣称本审查已独立复现应用桥接全部拒收。

风险：若子进程用系统编码输出中文而 Node 按 UTF-8 解码，JSON 可能仍可解析，但“代码”“最新价”等字段名损坏，导致实际有数据而归一化全部拒收。stdin 也应纳入 UTF-8 契约，避免含中文请求内容被错误解码。现有 mock 源测试和纯版本 helper 测试不能覆盖这一真实进程边界。

修复边界：保留 `-I` 隔离，通过显式 `-X utf8` 保证用于 JSON 传输的 Python 标准输入输出编码，不以移除隔离或仅补环境变量替代。父任务修复完成前不重读正在修改的文件。

验收：实际桥接进程的 stdin/stdout 编码为 UTF-8，中文字段和字符串无乱码；使用隔离目录及内存配置调用实际 `callPythonDataSource`，再执行公共池归一化，确认真实结果可产生非零事实行，并记录原始行数、有效行数、拒绝数与缺失字段。不得仅用直接 Python API 的 43 行代替应用链路证据；不调用持久化同步函数、不写生产数据库或配置。修复后的 UTF-8 参数须有隔离回归覆盖，非 AKShare 的 Python 3.10 门槛保持不变。

### R1 [P2] 显式交易所冲突被静默改写

最新状态：已关闭。Archimedes 最终交付版在 adapter 内局部拒绝冲突后缀，未要求修改共享行情代码规则；新增 9 项测试且目标文件独立 88/88 通过。下文保留原发现，具体最终复验见文末。

定位：`electron/main/services/publicLimitPoolAdapter.ts:108` 调用现有 `normalizeMarketStockCode`；该函数在 `electron/main/services/multiSourceMarketService.ts:19` 先剥除交易所后缀，再按首位重新推断。

实际后果：`000001.SH` 会被改为 `000001.SZ`，`600001.SZ` 会被改为 `600001.SH`，而不是拒绝矛盾输入。适配器现在接受带后缀输入，因此错误或发生格式漂移的源数据可能被重新归到另一证券，并在价格恰好接近时通过后续核对。当前代码测试覆盖正确后缀和去重，没有覆盖冲突后缀。

修复边界：在公共池适配器局部校验显式后缀与规范代码一致性即可；不要求重写所有行情来源的代码归一化。无后缀正常六位代码、已支持的合法大小写后缀仍可接受。进一步细化证券号段支持范围应明确约定，不能将任意首位规则宣传成证券主数据验证。

验收：冲突后缀被拒绝且计入 `rejectedRows`；合法 `.SH/.SZ/.BJ` 后缀及已有北京样本继续通过；同一合法证券不同表示仍只保留一行。同步不得写入由冲突代码改写得到的记录。

### R2 [P2] 组合条件先判未知，夸大“字段不足”的候选数量

最新状态：已关闭。Franklin 交付后的 viewModel 与新增组合边界测试已独立审查，目标文件 22/22 通过。下文保留原发现与关闭条件，具体修复证据见文末 R2 专项复验。

定位：`src/components/ShortTermStrategy/publicLimitPoolViewModel.ts:16` 至 `:23`。

实际后果：使用 `minBoards=2, maxOpens=0` 时，`limitTimes=1, openTimes=null` 已被连板条件明确排除，仍计入 `excludedUnknown`；对称的 `limitTimes=null, openTimes=2` 同样如此。补齐缺失字段不可能令这两条记录满足当前条件，因此不能把它们表示为尚无法判定的候选。

独立内存边界复现：使用本轮已经读取的原始 viewModel 源码快照，内存转译并执行，没有重写测试或实现文件。以上两个样本分别返回 `rows=[]、excludedUnknown=1、total=1`。这是额外边界执行结果，不计入 119 项 Vitest 测试。

修复边界：每个启用条件先计算 `pass/fail/unknown`；任一条件 `fail` 则明确排除；无 `fail` 但有 `unknown` 才增加 `excludedUnknown`；全部已满足才匹配。默认全部仍保留未知行。

验收：上述两个样本的 `excludedUnknown` 均为 0；`limitTimes=2, openTimes=null` 为 1；`limitTimes=null, openTimes=0` 为 1；全已知满足条件的记录被选中；未启用的条件不引入未知排除。
