# 1.19 筹码结构退出一致性候选

1.18 已正式发布；本文件记录下一轮本地候选，不表示 1.19 已验收或发布。已发布标签和安装包未修改。

## 本轮实现

- 新增筹码结构工作归属，停止时关闭新任务准入并取消已登记任务。
- 结构同步将取消信号传入日线、筹码表现和分布请求；请求返回后、落库和阶段切换前再次检查。
- 机构证据同步的独立调用与嵌套调用也登记到同一工作管理器。取消不替换事实或写入机构来源故障记录。
- 主进程退出时停止该管理器并等待任务收敛。筹码结构状态增加 cancelled，取消不增加失败数，不发送正常完成事件。
- cyq_perf 与 top_inst 接入已有的有界取消传输。已经销毁的窗口不再接收结构进度或完成推送。
- 产品内部候选版本递进为 1.19.0，未修改依赖声明或共享 Python。

已重建 1.19.0 Windows 应用目录，新增 daily、cyq_perf、cyq_chips、top_inst 四个请求边界的实际退出场景。四项均失败：未观察到目标请求被测试夹具拦截，因而无法进入受控退出验证，不能将结果当作取消或零写入通过。

依赖打包内容存在 globalThis.fetch 重新赋值代码，夹具拦截可能受首次加载影响；现有证据尚不足以证明其执行时序就是根因。需要先补强网络隔离，再观察实际请求与正常退出。只使用合成凭证，没有真实用户 Key、账户或订单，但不能将此失败测试声称为完全离线。

实际包测试及日志位于 D 盘构建区；未覆盖生产安装目录。新增测试的网络隔离修正已向用户提出，尚未获答复，未盲目重跑，未发布 1.19。

## 请求观察根因已定位（2026-10-12）

只读实际程序诊断确认 main realm 与 inspector realm 的 globalThis、fetch、process 和 Request 均相同，程序正常退出。失败场景的四份 will-quit 记录实际包含目标 API 请求，before 快照均已采集；此前零计数只是测试观察返回值，不能理解为请求未被拦截。

实际测试的 app.evaluate(stage => ..., stage) 把默认第一个 Electron 模块参数错当成了 stage，计数查找一直为零。必须改为接收模块及第二个 stage 参数后再重跑主动退出检查。先前依赖重设 fetch 的推测未获执行时序证明，已不作为本次根因，不需要冻结或替换程序的 fetch。

已将两处单元断言及这一处观察回调的修正合并请求用户决定，尚未修改这些错误、删除断言、抬高超时、重跑失败场景或发布候选。此前失败及超时记录保留；修正前不能判断退出取消验收通过。
